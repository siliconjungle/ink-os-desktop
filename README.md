# Ink OS Desktop

Desktop host for the shared Ink OS platform. Local instances have separate persistent directories and start with Finder, Preview and Ink Environment. Remote instances use the same web desktop.

The File menu includes **Check for updates…**. Published releases are checked for the current platform, architecture, version and build. Downloads are verified against their release manifest and saved in the private desktop profile. Preview installation is explicit: Ink OS finishes local work, quits, and opens the verified installer; replacing the application preserves data and connections outside its bundle. Update downloads are cancelled cleanly when quitting. Hosted apps continue to use server-published releases independently of the desktop binary.

The bundled CLI provides `ink-os desktop update check` and `ink-os desktop update download`. `--repository OWNER/REPO` selects a fork's publisher; `--channel preview|stable` selects its release channel; download accepts an owned private `--directory`. The default publisher and build live in `src/updates-config.json`. Private preview repositories require a Contents-read GitHub token in `INK_OS_UPDATE_TOKEN`; it is kept in memory and sent only to the GitHub API. Without access, the native dialog offers the release page for browser-based installation. Credentials are removed before following [release-asset redirects](https://docs.github.com/en/rest/releases/assets#get-a-release-asset).

For development, place the platform checkout next to this repository, install its dependencies, and build it. On macOS, Apple Command Line Tools and the active Node installation’s headers are needed to build the scroll-phase addon; set `INK_OS_NODE_HEADERS` if the headers are elsewhere. `npm start` and `npm run package` compile it automatically. Then:

```sh
npm ci
npm start
```

`INK_OS_PLATFORM_DIR` selects another platform checkout. The Connections menu opens the local instance or a saved hosted HTTPS connection. New desktop profiles select Local by default. The local host generates private credentials and authenticates its window automatically.

Connections accepts an exact HTTPS origin and an optional account token. It verifies the host identity before sending the token and verifies the account before creating a desktop session. Account keys need the `computer` scope; app and service credentials cannot sign in to the desktop. Tokens stay in private client files and are omitted from profile lists and session names. Rotating a key for the same verified account preserves its browser session, IndexedDB and pending edits, while immutable client files keep running commands bound to their original credentials. Different accounts, host identities and anonymous-to-account transitions use separate browser sessions. Without a saved token, browser sign-in remains available, while authenticated CLI calls need an explicit credential.

A connection switch becomes active after its new window loads successfully. A failed switch preserves the previous selection and window. **Save and open** and **Pin identity** explicitly persist their verified credential or identity update first; a later navigation failure preserves that saved update and the existing window. Running commands retain their original client file. Use Connections for desktop credential changes; an independent CLI `login` requires an explicit caller override so it cannot overwrite a desktop client generation.

Earlier unbound connection generations retain their client files and browser data. On first verified use, the current legacy browser partition is bound to its account without moving its cache. The core's `retainedSessions` diagnostics list older generations; `recoverLegacySession` can select one only after its old and current credentials both verify to the same account and host boundary. Revoked or unknown historical credentials leave that data preserved and recovery blocked. Connections does not copy caches across accounts or delete old partitions.

Hosted connections pin the server's instance identity. For an older host that does not advertise an identity, explicitly enable origin compatibility in Connections. If that host later advertises an identity, use **Pin identity** before signing in again. `INK_OS_REMOTE_URL=https://ink.example.com` selects or adds a hosted connection at startup; a new legacy connection also requires `INK_OS_REMOTE_MODE=origin-compatibility`.

The first development launch downloads the pinned Electron runtime if it is missing. `INK_OS_DESKTOP_DATA_DIR` selects a separate private profile. Local profiles keep their address across restarts so browser storage remains available. Reopening a window reuses its host. Switching connections keeps local background work running, and remote startup does not start a local host or initialize a native toolchain. Quitting drains background work before stopping an owned host, including when a remote view is selected. A surviving host is authenticated and reconnected without starting another writer.

Ink apps use the shared platform's JavaScript runtime by default. Explicit native builds are exposed through its API, CLI and SDK; a compatible cached native artifact can run without an installed compiler. On macOS arm64/x64, an explicit native build can install the pinned official Rust/Cargo components into the private instance profile. Startup and status never download them. Apple Command Line Tools or Xcode must already provide clang and the macOS SDK; JavaScript remains available when native prerequisites are missing. The installer checks archive hashes, retains upstream notices and leaves system Rust, Cargo and PATH unchanged. Managed installation is currently limited to macOS; standalone platform hosts can use a configured system toolchain.

The pinned platform supports [typed incremental Ink interfaces](https://github.com/siliconjungle/ink-os-platform/blob/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/docs/typed-ui.md): checked view/event types, stable widget identities, component state dependencies, shared relational query snapshots and local form drafts. The [Ink-only example](https://github.com/siliconjungle/ink-os-platform/tree/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/examples/typed-ui) includes forms, lists, tables and navigation. Desktop uses the DOM adapter in its shared web interface; native Ink computation can produce those views, while native widgets require a separate adapter implementing the documented layout, input, accessibility and lifecycle contracts. This source pin takes effect in the next desktop build; it does not replace an already installed package.

The pin also includes [connected system planning](https://github.com/siliconjungle/ink-os-platform/blob/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/docs/system-planning.md): compiler-derived module summaries, independently checked app releases, reusable build caches and pinned typed query links. The [Tables plus dashboard example](https://github.com/siliconjungle/ink-os-platform/tree/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/examples/tables-system) retains one exported query for both apps and delivers ordered view patches with exact source versions, bounded replay and snapshot recovery. The [delivery comparison](https://github.com/siliconjungle/ink-os-platform/blob/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/docs/benchmarks/retained-query-2026-11-04.md) records JavaScript/native histories and measured latency, execution counts and transfer bytes. The host uses bounded long-poll delivery through the shared SDK and desktop MessagePort bridge.

The platform pin also includes [bounded data-path planning](https://github.com/siliconjungle/ink-os-platform/blob/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/docs/data-path-planning.md) for declared World Tables UI queries. Builds compare scan, fixed-index and maintained-result recipes using committed workloads; releases replay checked contracts and use an explicit scan fallback when their guards no longer apply. The [planned storage example](https://github.com/siliconjungle/ink-os-platform/tree/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/examples/planned-storage) passes the shared DOM adapter checks with JavaScript and native Ink computation. These are trusted host storage recipes; arbitrary Ink state lowerings still require separate Ink equality proofs.

The pin includes [reusable kernel-checked proof units](https://github.com/siliconjungle/ink-os-platform/blob/ec57504eb24a8d71dd6b2fa1401e00dfeb5ddbfe/docs/proof-units.md). The Tables demonstration admits mathematical dependencies independently, discards checked theorem bodies and reuses unchanged units across releases. Complete source bindings, fold equations and target artifacts remain checked; eviction or restart replays the full required closure. The linked study records reduced proof size, admission time and process memory with matching generated JavaScript/Rust source. Admission deadlines include queueing and resource waits; equivalent descriptor property ordering reuses checked units, and phase/ABI-byte counters include completed work from rejected requests.

Build a desktop package with `npm run package`. The builder takes the exact platform revision in `platform.json` from the selected platform checkout, installs its locked dependencies in an isolated workspace, and builds the shared interface. It includes Electron, the platform runtime, the Ink compiler, production dependencies, Git core and its corresponding source/build recipe. The installed app does not need Node or Git installed separately. Fresh instances include Finder, Preview and Ink Environment.

macOS builds produce a drag-to-Applications DMG. Linux builds produce a portable archive; Linux graphical validation and Windows packaging are pending. Local macOS builds use an ad hoc signature. Set `INK_OS_MAC_SIGN_IDENTITY` for a developer identity and optionally `INK_OS_MAC_NOTARY_PROFILE` for an existing Keychain notarization profile. Signing and verification failures stop the build. Credentials stay outside package manifests and source history.

The packaged CLI is `Ink OS.app/Contents/Resources/ink-os` on macOS and `ink-os` beside the executable on Linux. It captures the desktop's selected connection when each command starts; switching the GUI later does not retarget that command. `INK_OS_CONFIG`, `INK_OS_URL`, `INK_OS_TOKEN` or `--url` are explicit caller overrides. The CLI does not start a local host: open Local in the desktop before using its authenticated APIs. It can initialize/build/deploy Ink apps and use the same command, workflow and data APIs as the web version. For example:

```sh
"/Applications/Ink OS.app/Contents/Resources/ink-os" init ./my-app --slug my-app
"/Applications/Ink OS.app/Contents/Resources/ink-os" deploy ./my-app
```

## Desktop gestures

Two-finger horizontal swipes switch desktops anywhere in the active Ink window, including unselected app frames. Each new physical gesture moves one desktop and stops at either end. Switches slide left or right in desktop order over 320 ms, with the toolbar and Dock stationary. Reduced-motion preferences use an immediate switch. Swipe up with two fingers on the desktop background or an app window title bar to shrink the desktop into its selection card. Desktop selection uses a controlled track without a scrollbar: left/right chooses a centered, highlighted desktop, and swiping down expands into that choice. The current desktop remains live in its miniature. The selection background and controls fade in/out, and clicks and keyboard input can finish the motion without being swallowed. Selecting another card or app returns to that selection. These transitions take 340 ms and respect reduced motion. Vertical scrolling and pinch gestures remain available in app content. On macOS, an app-local AppKit scroll monitor distinguishes each physical swipe from its momentum, including rapid consecutive swipes. It does not change macOS gesture settings or request global input access.

On macOS, the Desktops menu includes a persistent **Three-finger desktop switching** option (off by default) and gesture help. Native left/right swipes switch Ink desktops even when an app frame has focus. macOS must pass the gesture to Ink: configure switching full-screen apps to use four fingers, and page swiping to allow three fingers, in System Settings → Trackpad → More Gestures. System-reserved gestures take priority.

The native bridge forwards foreground-window state, physical gesture starts and validated swipe directions to the selected desktop. App frames forward bounded wheel data through ordinary DOM messages, including nested frames; the wrapper installs this compatibility bridge for existing apps. App frames receive no Node access or native IPC capabilities. Dialogs, quick previews and active drags block switching. Ctrl Alt Left/Right and the Desktops menu remain available without trackpad configuration.
